# Карта архитектуры проекта

Этот файл описывает **текущее расположение кода и основные точки расширения**. Правила разработки и обязательные ограничения находятся в `AGENTS.md`. При расхождении с этой картой сначала сверяйся с фактическим кодом. Файлы в `.workai/plans/` — планы работ, а не гарантированное описание реализованного состояния.

## Структура верхнего уровня

| Путь | Назначение |
|---|---|
| `main.py` | Создание FastAPI-приложения, подключение статических файлов и агрегированного роутера. |
| `api/routers/` | HTTP/UI-адаптеры: принимают запрос, преобразуют ввод/вывод и вызывают логику приложения. Здесь не размещается основная логика возможностей. |
| `modules/` | Функциональные возможности продукта, сгруппированные по назначению или сервису. Ядро должно иметь вызываемую из Python точку входа и не зависеть от FastAPI. |
| `shared/` | Общие инфраструктурные компоненты и утилиты, которые действительно используются несколькими возможностями. Это не место для логики, специфичной одной функции продукта. |
| `scenarios/` | Кодовые сценарии, координирующие функциональные модули и общие утилиты через Python-точки входа; содержит сценарий подготовки NEWS-метатегов. |
| `config/` | Общая конфигурация приложения. Настройки конкретной возможности или сервиса хранятся рядом с её кодом. Секреты читаются из окружения; не записывать их в документацию. |
| `tests/` | Автоматические тесты и отдельно расположенные ручные инструменты запуска. |
| `templates/`, `static/` | HTML-шаблоны и статические ресурсы пользовательского интерфейса. |
| `worksheets/`, `sources/` | Рабочие таблицы и исходные данные, используемые некоторыми операциями. Не считать их Python-пакетами. |
| `temp_files/` | Каталог временных результатов; создаётся или используется во время работы приложения. Не хранить в нём исходный код. |

## Текущие функциональные пакеты

### `modules/xmlriver/`

- `service.py:run_module` — общий программный запуск XMLRiver-возможности; проверяет входные данные и конфигурацию, затем вызывает функцию из реестра. Для TOP выдачи доступны ID `serp` (Yandex) и `google_serp` (Google).
- `registry.py` — сопоставляет идентификаторы `frequency`, `popular`, `serp`, `google_serp` с функциями сбора данных.
- `xmlriver_frequency.py`, `xmlriver_popular.py`, `xmlriver_serp.py`, `xmlriver_google_serp.py` — реализации отдельных операций с XMLRiver.
- `settings.py` — настройки именно XMLRiver, включая независимые параметры поисковой выдачи Yandex и Google.
- `export.py` — формирование XLSX-результатов.
- `api/routers/xmlriver.py` — HTTP-адаптер: UI-маршруты принимают фразы и возвращают XLSX; `POST /api/xmlriver/google_serp` принимает JSON `{\"phrases\": [...], \"top_n\": 10|20|30}` и возвращает результаты.

Для прямого вызова из другого Python-кода используй `modules.xmlriver.service.run_module`, например `run_module("google_serp", phrases, top_n=20)`, а не HTTP-запрос к собственному приложению.

### `modules/relevance_analyzer/`

- `service.py:run_analysis` — публичный вход для прямого Python-вызова; принимает проверенную конфигурацию и возвращает объект `Relevance` с рассчитанной статистикой.
- `config_input.py` — чтение исходного TXT-формата и JSON-конфигураций.
- `relevance.py`, `text_analyzer.py`, `morph.py`, `stopwords.py` — независимое от FastAPI ядро анализа и нормализации.
- `export.py:export_xlsx` — формирует четыре XLSX-отчёта; строки экранируются от формул.
- `api/routers/relevance_analyzer.py` — веб-адаптер запуска и скачивания ZIP-архива; внешние URL и перенаправления проверяются перед загрузкой.

Для Python-сценария вызывай `modules.relevance_analyzer.run_analysis(config)` напрямую. Веб-путь: `/relevance-analyzer` → `run_analysis` → четыре XLSX-файла в ZIP.

### `modules/openai_api/`

- `service.py:chat_completion` — публичный независимый от FastAPI клиент OpenAI Chat Completions; принимает OpenAI-совместимый формат, отправляет HTTPS-запрос и возвращает JSON API.
- `settings.py` — читает `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL` и `OPENAI_TIMEOUT_SECONDS` из окружения; ключ не логируется.
- `api/routers/openai_api.py` — REST-адаптер `POST /api/openai/chat/completions`; сетевой вызов выполняется вне event loop. Endpoint не требует клиентского токена и должен быть доступен только из доверенной сети.
- `templates/dashboard.html` — форма отправки запроса с настройкой температуры и максимальной длины ответа.

Для прямого вызова из Python используй `modules.openai_api.chat_completion(messages, model=..., temperature=...)`. `OPENAI_BASE_URL` можно настроить на сервер OpenAI или совместимый API. Ключ провайдера хранится только в `.env` на сервере.

### `modules/xmlstock/`

- `service.py:request_xmlstock` — публичный независимый от FastAPI клиент для Яндекс XML Proxy, Яндекс Live, Google XML Search и Яндекс Wordstat; возвращает HTTP-статус, тип содержимого и тело ответа.
- `validation.py` — фиксированные endpoint, режимы, HTTP-методы и документированные параметры с проверкой форматов и диапазонов.
- `settings.py` — читает `XMLSTOCK_USER`, `XMLSTOCK_KEY` и `XMLSTOCK_TIMEOUT_SECONDS` из серверного окружения; учётные данные не передаются из браузера и не выводятся в логах.
- `api/routers/xmlstock.py` — REST-адаптер `POST /api/xmlstock/{tool}`; запускает общий клиент вне event loop. Endpoint следует выставлять только во внутреннюю/доверенную сеть, так как запросы расходуют квоту аккаунта.
- `templates/dashboard.html` — карточка с вкладками четырёх инструментов; ответ провайдера выводится как текст.

Для прямого вызова из Python используй `modules.xmlstock.request_xmlstock(tool, params, output_format=..., method=...)`. XML Proxy поддерживает GET/POST; остальные инструменты — GET. Wordstat всегда возвращает JSON.

### `modules/vilmed/`

- `overspam.py:overspam_vilmed` — обрабатывает загруженный XLSX и ищет совпадения по справочнику PostgreSQL; возвращает DataFrame для XLSX-выгрузки.
- `repository.py` — импортирует лист `Готовый список ID` из `worksheets/work_vilmed.xlsx` и читает `vilmed_reference_categories`; по умолчанию импорт разрешён только в пустую таблицу, явная замена выполняется атомарно.
- `import_reference.py` — отдельная CLI-команда для импорта справочного листа; при старте приложения не запускается.
- `import_workbook.py` — переносит пять остальных листов книги в отдельные таблицы; каждую таблицу заполняет транзакционно, а уже непустые пропускает без замены данных.
- `migrations/versions/0001_*.py` создаёт таблицу справочника, а `0002_*.py` — отдельные таблицы для `Плитка тегов`, `categories_id`, `bar_tags`, `menu_categories` и `all_products`.
- `category_menu.py:update_cat_menu_vilmed` — бизнес-операция пока продолжает обновлять рабочий XLSX; перенос листа в БД не переводит эту операцию автоматически.
- `api/routers/vilmed.py` — HTTP-адаптер для операций Vilmed; передаёт общую БД-фабрику в `overspam_vilmed`.

### `modules/site_tools/`

- `bar_tags.py:link_selection_bar_tags` — основная функция обработки bar tags.
- `open_links.py:open_links_in_browser` — открытие переданного списка ссылок в системном браузере; интерфейс предоставляется через API и шаблон, отдельное администрирование функции не требуется.
- `update_sheet_bar_tags.py:main` — отдельный процесс обновления таблицы bar tags; перед повторным использованием проверь его входы, побочные эффекты и фактический способ запуска.
- `api/routers/site_tools.py` — HTTP-адаптеры операций с bar tags и ссылками.

Существующий код развивается неравномерно: не все старые функции уже оформлены как самостоятельные модули с полным контрактом. При добавлении нового функционала следуй правилам `AGENTS.md`, не копируя автоматически устройство legacy-файлов.

### `scenarios/auto_news_meta_tags.py`

- `run_auto_news_meta_tags(urls)` — публичный сценарий: получает список URL, собирает заголовок и основной текст через `shared.page_content`, подставляет их в `shared/prompts/auto_news_meta_tags.md`, вызывает `modules.openai_api.chat_completion` и возвращает результат отдельно для каждой страницы.
- `api/routers/auto_news_meta_tags.py` — интерфейсный адаптер `/auto-landings/meta-tags-news`; успешные ответы сохраняются как отдельные TXT-файлы с безопасными именами по заголовкам и выдаются одним ZIP-архивом.
- `templates/dashboard.html` — карточка «Авто лендинги» и вкладка «Мета-теги NEWS» для запуска сценария.

## Общие компоненты

- `shared/database.py:create_database_engine`, `check_database_connection` — общие SQLAlchemy-инструменты подключения; URL передаётся только из серверного окружения, а движок создаётся и закрывается в lifespan приложения.
- `shared/phrase_import.py:parse_phrases` — разбор фраз из текста или XLSX.
- `shared/temp_storage.py:manage_temp_dir` — создание, получение и удаление временных каталогов.
- `shared/log_stream.py:run_with_log_capture`, `stream_session` — захват вывода задачи и передача логов через SSE.
- `shared/link_checker.py:check_link` — проверка доступности ссылки.
- `shared/page_content.py:fetch_page_content` — получение публичной HTML-страницы с ограничением размера/редиректов и извлечение текста через CSS-селекторы.
- `shared/prompt_templates.py:load_prompt_template`, `render_prompt_template` — загрузка Markdown-шаблонов из `shared/prompts/` и проверенная подстановка `{{variables}}`.
- `shared/prompts/` — общие текстовые prompt-шаблоны, не содержащие логики исполнения.
- `shared/directory_cleanup.py:clear_directory` — очистка содержимого указанного каталога.

Перед созданием утилиты проверь, действительно ли она нужна нескольким возможностям. Если логика относится только к одной возможности, оставь её в соответствующем пакете `modules/`.

## Поток вызова

1. `main.py` создаёт приложение и подключает `api.routers.router`.
2. `api/routers/__init__.py` собирает отдельные роутеры страниц, системных функций и функциональных пакетов.
3. Роутер проверяет и преобразует HTTP-ввод, затем вызывает публичную Python-функцию функционального пакета или общий сервис.
4. Сценарий напрямую вызывает публичные точки входа модулей и общих утилит, не проходя через FastAPI.
5. Общая инфраструктура из `shared/` подключается по необходимости; она не должна содержать бизнес-логику конкретного сценария или продукта.

Для XMLRiver конкретная цепочка выглядит так: `api/routers/xmlriver.py` → `modules/xmlriver/service.py:run_module` → `modules/xmlriver/registry.py` → функция операции в `modules/xmlriver/` → `modules/xmlriver/export.py`.

Для NEWS-метатегов цепочка выглядит так: `api/routers/auto_news_meta_tags.py` → `scenarios/auto_news_meta_tags.py:run_auto_news_meta_tags` → `shared.page_content` → `shared.prompt_templates` → `modules.openai_api.chat_completion` → ZIP с отдельными TXT-файлами.

Для Vilmed приложение читает `vilmed_reference_categories` в `overspam`; остальные пять листов вручную переносятся командой `python -m modules.vilmed.import_workbook --target-database ИМЯ_БАЗЫ` в независимые таблицы. Все шесть листов хранятся в PostgreSQL, но операции меню и остальные XLSX-сценарии пока продолжают работать с книгой Excel.

## Как добавлять функциональность

### Новый функциональный модуль

1. Создай пакет `modules/<capability>/` с понятным именем.
2. Реализуй основную операцию как публичную Python-функцию с ясными входами, результатом и обработкой ошибок; не импортируй FastAPI в ядро.
3. Если нужен UI/API, добавь или расширь роутер в `api/routers/`. Роутер должен вызвать ту же функцию, доступную сценарию, а не копировать её бизнес-логику.
4. Подключи новый роутер через `api/routers/__init__.py`, если он отдельный.
5. Добавь офлайн-тесты на логику и контракт; внешние сервисы подменяй на границе вызова.

### Новая общая утилита

1. Создавай её в `shared/` только при реальном повторном использовании или явно общей инфраструктурной роли.
2. Сохраняй независимость от FastAPI и от конкретного продуктового сценария.
3. Дай имя, описывающее действие или ответственность, и проверь существующие компоненты на дублирование.

### Новый сценарий

1. Создай сценарий в `scenarios/` как последовательность вызовов публичных функций модулей.
2. Не помещай его orchestration-логику в `shared/` и не вызывай HTTP-маршруты из Python-кода.
3. Добавь тесты, подменяя внешние API и проверяя передачу данных между этапами.
4. Добавляй сценарий в реестр только если реестр реально используется вызывающим кодом; пустой `scenarios/registry.py` сам по себе не является работающим механизмом запуска.

## Проверки и первый запуск PostgreSQL

- Автоматические тесты: `python -m unittest discover -s tests -p 'test*.py'`.
- `tests/run_test.py` — ручной XMLRiver-запуск с внешним API, а не автоматический тест. Не запускать его без явной необходимости и корректной конфигурации окружения.
- После изменения публичных точек входа обновляй эту карту и тесты вместе с кодом.
- Зависимости PostgreSQL добавлены в `requirements.txt`; пароль и полный `DATABASE_URL` хранятся только в окружении процесса/контейнера, не в репозитории. Не публикуй порт PostgreSQL в интернет.
- До миграции вручную проверь, что `DATABASE_URL` указывает на нужную базу. Если приложение запущено в другом контейнере, оба контейнера должны быть в общей Docker-сети; имя хоста `my_db` работает только при наличии такого DNS-алиаса в этой сети.

Для импорта книги Vilmed:

1. Установи зависимости проекта и задай `DATABASE_URL` в окружении приложения.
2. Проверь целевую базу через настроенное подключение; не удаляй и не пересоздавай базу.
3. Выполни `alembic current`, затем `alembic upgrade head`. Миграции добавляют таблицу `vilmed_reference_categories` и пять независимых таблиц для остальных листов.
4. Импортируй справочник командой `python -m modules.vilmed.import_reference --target-database ИМЯ_БАЗЫ`, если он ещё не загружен.
5. Импортируй остальные листы командой `python -m modules.vilmed.import_workbook --target-database ИМЯ_БАЗЫ`. Импортёр проверяет целевую базу, проверяет заголовки книги, вставляет только в пустые таблицы и пропускает уже заполненные.
6. После импорта сверь `COUNT(*)` каждой таблицы с количеством строк данных в соответствующем листе. Для повторной загрузки сначала выясни, почему таблица уже заполнена; автоматического удаления или замены данных нет.

`DATABASE_URL` с PostgreSQL в Docker должен использовать адрес, доступный именно контейнеру приложения, а не DBeaver. Передавай URL только через переменные окружения; приложение не выполняет миграции или импорт автоматически при старте.
